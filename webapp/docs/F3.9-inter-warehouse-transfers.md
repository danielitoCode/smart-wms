# F3.9 — Inter-warehouse Transfers

Branch: `svelte-webapp`  
Scope: `webapp/`, Flask API, database migration and PostgreSQL integration tests.

## Contract

- `GET /api/admin/inter-warehouse-transfers?limit=N&from_warehouse_id=&to_warehouse_id=` returns completed movement history.
- `POST /api/admin/inter-warehouse-transfer` accepts item, source/destination warehouse and bin IDs, integer quantity (1–100,000), optional reason (max 200), and required UUID `idempotency_key`.
- The history API is the detail surface. No individual detail endpoint or approval lifecycle exists.
- A transfer spanning multiple lot rows creates one `bin_transfers` row per lot while preserving `lot_number`; the receipt returns `transfer_ids` and the first `transfer_id` for compatibility.

## Frontend

- Source and destination warehouse selectors load only active warehouses returned by `/api/warehouses/list`, which is SQL-scoped to the current user's assignments.
- Source and destination bin typeaheads are independent and query `/api/lookup/bin/search?q=&warehouse_id=`. Results are SQL-scoped by the authenticated user and constrained to the selected warehouse; changing a warehouse clears its selected bin.
- Product typeahead uses the operational item search endpoint and only offers active items available in the user's warehouse scope.
- The UI never accepts manually typed IDs as selections. It sends selected entity IDs only after a result is chosen.
- The transfer submission retains one UUID idempotency key after a network/HTTP failure, so an unchanged retry replays the original server receipt. Editing any field invalidates the local key.
- History source/destination filters are sent to Flask and are also checked locally by the use case. The server scope remains authoritative.

## Backend security and data integrity

- Both warehouse IDs must identify distinct, active warehouses and must both be inside the live user's warehouse scope. The SQL lookup scopes both IDs before returning data, so unknown, inactive, and unauthorized IDs share a non-enumerating 404 response. Each side is also checked with `check_warehouse_access`.
- Source and destination bin lookups require the supplied warehouse ID, active bins, and the SQL warehouse scope.
- History applies two SQL predicates: the source warehouse **and** destination warehouse must be authorized. Optional origin/destination filters are applied server-side. Limits and malformed filters are rejected.
- A transaction-scoped PostgreSQL advisory lock serializes requests for the same (username, idempotency key). A durable receipt table has a composite primary key on (user_id, idempotency_key), stores the normalized request and original response, replays identical requests without another inventory mutation, and returns 409 if a key is reused with a different payload.
- Both item/bin advisory locks are acquired in deterministic bin-ID order before inventory row locks. Source inventory rows are locked with `FOR UPDATE`, available stock is calculated as `quantity_on_hand - quantity_allocated`, and allocated units cannot be moved.
- Stock is decremented/incremented per lot, transfer rows and both warehouse audit entries are written, backorders are evaluated, and the idempotency receipt is persisted in the same database transaction. Notifications are dispatched only after commit.
- Migrations `083_inter_warehouse_transfer_idempotency.sql` and `084_inter_warehouse_transfer_user_identity.sql` create the durable receipt table and upgrade earlier username-keyed installations to immutable user IDs. `084` is repeatable and removes orphaned receipts for deleted usernames. `db/schema.sql` includes it for fresh database initialization; the test fixture truncates it between tests.

## Tests added

- Source-only, destination-only, neither, and both-warehouse authorization.
- History visibility only when the user can access both ends; server-side origin/destination filters and malformed-filter validation.
- Allocated source quantity cannot be transferred.
- Repeated same-key request returns the identical receipt and changes stock only once; same key with a different payload returns 409.
- Forced failure after inventory mutation proves transaction rollback of stock, transfer rows, and idempotency receipt.
- PostgreSQL tests verify same-key advisory-lock serialization and concurrent source-row locking (two simultaneous 4-unit moves against 5 units yield one success and one rejection); migration test upgrades username-keyed receipts to user IDs and reapplies the migration.
- Frontend tests cover warehouse-scoped bin search, domain constraints, and history filtering.

## Remaining validation

- Automated CI must pass on the final commit after these changes.
- Run the PostgreSQL integration suite against a dedicated test database with migration 083 applied; no production database should be used for tests.
- Browser-level manual verification remains useful for dropdown keyboard/touch behavior and retrying after a simulated timeout.
