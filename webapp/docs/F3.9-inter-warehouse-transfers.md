# F3.9 — Inter-warehouse Transfers

Branch: `svelte-webapp`  
Frontend scope: `webapp/`. Flask is inspected as the source of truth for the contract; backend security and transaction gaps are recorded explicitly and are not represented as solved by UI validation.

## Contract confirmed

- `GET /api/admin/inter-warehouse-transfers?limit=N` returns `{ transfers: [...] }`.
- Each row is a completed, single-item movement: `transfer_id`, item/SKU/name, source/destination bin and warehouse IDs/codes/names, quantity, actor, timestamp, and `status: "completed"`.
- `POST /api/admin/inter-warehouse-transfer` accepts `item_id`, `from_bin_id`, `from_warehouse_id`, `to_bin_id`, `to_warehouse_id`, `quantity`, and optional `reason`; it returns a committed-movement receipt with `201`.
- There is no individual detail endpoint and no pending/approval lifecycle. The list is the movement history. The backend schema constrains quantity to an integer from 1 through 100,000.
- React uses authorized active warehouses from `/api/warehouses/list`, remote bin search by warehouse, item search, and the same list/create endpoints. The current Svelte screen still has numeric ID inputs; this is a functional parity gap.

## Frontend changes in this iteration

- Domain validation now requires safe positive integer IDs, distinct source/destination warehouses, integer quantity in the backend range (1–100,000), and a reason no longer than 500 characters.
- History use case supports source and destination warehouse filters and validates the 1–500 request limit.
- State prevents overlapping create submissions, keeps load errors visible, and exposes independent source/destination filters.
- Data source clamps list limits to the backend maximum and safely handles a missing/non-array `transfers` payload.
- Screen exposes source and destination history filters.
- Added use-case tests for filtering, validation boundaries, and reason normalization.

## Backend security and integrity findings — BLOCKING

The inspected Flask handlers are not sufficient to claim secure multi-warehouse transfers:

1. **Create authorization is missing for both warehouses.** The handler verifies that each bin belongs to the warehouse ID supplied in the body, but does not call `check_warehouse_access` for either warehouse. A non-admin with access to only one side can currently submit a movement involving an unauthorized warehouse.
2. **Create lookup is not SQL-scoped.** Source and destination bin lookups use the supplied IDs and warehouse IDs but do not add `warehouse_scope_clause`. Item lookup is global (reasonable for catalog identity), but inventory access must be scoped by the source warehouse and destination access independently verified.
3. **History is not SQL-scoped.** The GET query joins both warehouses but has no source/destination scope predicate. A user granted the page permission can receive records involving warehouses outside their assignment. The UI's client-side filters are presentation only and are not an authorization boundary.
4. **No idempotency contract.** Each POST creates a new `bin_transfers` row with a fresh UUID. A client retry after a timeout can repeat the stock decrement/increment. A request idempotency key must be persisted under a unique constraint and replay the original receipt.
5. **Concurrency/atomicity needs stronger proof.** The handler commits the source decrement, destination increment, backorder release, transfer row, and audit records together, which is a useful transaction boundary. However, it reads source `quantity_on_hand` without `FOR UPDATE`, does not check `quantity_allocated`, and has no idempotency serialization. The current code therefore does not prove safe concurrent transfers or no double movement.
6. **Rollback and notifications.** Backorder notifications are dispatched after commit, which is appropriate. Add tests that force failures before commit and assert inventory, transfer rows, and both audit entries roll back together.

### Required backend implementation

- Validate both warehouse IDs as distinct, existing, active warehouses.
- Verify source and destination access separately with `check_warehouse_access`; use SQL scoping for history and any resource lookup whose existence must not leak. For history, a non-admin must see only rows where **both** joined warehouse IDs are in their allowed scope (not merely either side).
- Lock the source inventory row with `SELECT ... FOR UPDATE`, re-read available quantity under the lock, and reject movement beyond unallocated availability. Lock ordering must be deterministic where multiple rows are involved.
- Add a client-supplied idempotency key with a database unique constraint and store the committed response. Replays return the same receipt without applying stock changes again.
- Add PostgreSQL integration tests for access to both/source-only/destination-only/neither, scoped multi-warehouse history, simultaneous transfers, duplicate/replayed requests, and forced rollback.
