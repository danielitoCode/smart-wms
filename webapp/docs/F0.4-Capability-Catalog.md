## 1. Propósito y reglas del registro

Este catálogo asigna una identidad estable a cada capacidad que debe protegerse durante la migración React → SvelteKit. El ID identifica el comportamiento/contrato de negocio, no el nombre de una pantalla, ruta, archivo ni implementación.

Reglas:

1. Los IDs no se reciclan ni cambian por renombrar rutas, mover componentes, dividir módulos o reorganizar features.
2. Si una capacidad se divide, el ID original permanece como capacidad padre y se crean IDs hijos; si dos capacidades se consolidan, sus IDs antiguos se conservan como alias históricos y se registra la relación.
3. La ruta o componente Svelte es una ubicación de implementación, no la identidad de la capacidad.
4. El catálogo no declara paridad. El estado funcional se obtiene de la matriz operativa y de evidencias R10.3/R10.4.
5. La ausencia de evidencia se registra como `PENDIENTE` o `NO VERIFICADO`; nunca se rellena por inferencia.
6. Los nombres de tests, archivos, permisos y endpoints se mantienen en R10.1/auditorías cuando ya están detallados. Este catálogo enlaza esa fuente en lugar de duplicarla y crear dos fuentes de verdad.
7. Una capacidad solo queda protegida cuando alcanza `RESOLVED` o `RESOLVED_WITH_BACKEND_LIMITATION` con SHA y pruebas; `DISCOVERED`, `IN_PROGRESS` e `INTEGRATED` no son estados de aceptación.

### Esquema obligatorio de cada registro

| Campo | Regla |
|---|---|
| ID | Clave permanente y única. |
| Dominio / capacidad | Resultado de negocio observable. |
| Propietario | Feature/caso de uso que implementa la regla; no el consumidor. |
| Referencia React | Ruta y fuente original o `NO APLICA` cuando no existe espejo React. |
| Destino Svelte | Ruta/feature candidata observada en F0.3; puede cambiar sin cambiar el ID. |
| Dependencias | IDs de capacidades compartidas o de negocio que deben estar disponibles primero. |
| Permisos / almacén | Referencia al grant/función y clasificación de scope en R10.1; desconocidos permanecen pendientes. |
| Archivos / consumidores | Rutas de implementación y consumidores concretos en R10.1; completar a nivel de archivo/test al desarrollar o cerrar cada operación. |
| Pruebas / evidencia | Referencias exactas de R10.1, runbook y CI; no se presume cobertura por tener un test cercano. |
| Estado | Estado funcional según evidencia. El estado inicial de este catálogo no equivale a `RESOLVED` de la funcionalidad. |

## 6. Campos de trazabilidad por completar durante F2/F4

El catálogo fija IDs, propietarios lógicos y dependencias. No inventa el detalle que todavía falta auditar. Para cada ID, R10.1/R10.2 debe mantener o completar:

- Archivos React exactos, handlers, validaciones, transiciones y estados posteriores.
- Archivos Svelte exactos: rutas, screens, view-models, use cases, puertos, adaptadores, DTO y componentes.
- Consumidores concretos (importadores, navegación, otros casos de uso, acciones compartidas y enlaces).
- Grants de página/función y enforcement Flask exacto.
- Clasificación de almacén por endpoint: `SERVER_ENFORCED`, `FRONTEND_GUARD_ONLY`, `GLOBAL` o `NOT_APPLICABLE`.
- Tests exactos por capa y por operación, distinguiendo mocks de integración/persistencia real.
- SHA de aceptación, resultado, reportes y links de evidencia.

No se bloquea F0.4 por campos cuyo cierre depende de implementar/verificar cada operación, pero esos campos quedan explícitamente pendientes y son gates obligatorios antes de proteger una capacidad. La fuente de detalle permanece en R10.1 para evitar duplicación.

## 7. Riesgos conocidos que el catálogo no resuelve ni oculta

- Rutas legacy placeholder y cambios de slug identificados en F0.3 siguen siendo tareas de routing/paridad, no aliases funcionales por el hecho de estar catalogados.
- CycleCountApproval y RMA mantienen mappings dudosos/no dedicados; no se fusionan con Inventory Adjustments o Returns sin demostrar equivalencia.
- Warehouse scope no se infiere de un filtro UI ni de un query param; los gaps de Flask ya descritos en R10.1 continúan abiertos.
- R6.2 Packing y R6.3 Shipping son capacidades Svelte sin espejo React operativo; se contrastan con contrato y reglas de negocio.
- La presencia de una capacidad en este registro no significa que esté implementada, integrada, probada o aceptada.

## 9. Control de cambios del catálogo

Añadir un ID solo cuando se descubre una capacidad funcional diferenciada que no cabe en una existente. Registrar fecha, motivo, origen, dependencia, consumidor y referencia de prueba. No usar IDs basados en nombres de pantalla/ruta. Las divisiones y consolidaciones requieren tabla de alias/historial y revisión de todas las referencias de R10.1, runbooks y pruebas.
