# F1.1 — Bootstrap, layout raíz, carga inicial, hydration y recuperación

**Estado:** IN_PROGRESS — implementación inicial publicada; pendiente validación local completa y CI sobre el HEAD candidato.  
**Rama:** `svelte-webapp`  
**HEAD de implementación inspeccionado:** `abe3c06951564fddc4693d9076e50051ecb2f8f6`  
**Crédito:** 0% hasta superar los gates de validación y cerrar la tarea.  
**Ámbito:** `webapp/` SvelteKit. No modifica Flask, contratos API, autenticación, grants ni reglas de negocio.

## 1. Objetivo

Asegurar un ciclo de vida único y observable para el arranque de la aplicación:

1. El documento SSR declara un estado inicial determinista.
2. La aplicación se hidrata con el mismo estado inicial.
3. El bootstrap del navegador inicializa tema e idioma en orden controlado.
4. La aplicación solo publica `data-app-state="ready"` cuando los inicializadores raíz terminan.
5. Un fallo de inicialización presenta una pantalla recuperable y permite reintentar.
6. Un error de renderizado descendiente queda aislado por un `svelte:boundary`, con recuperación de vista o recarga completa.
7. Los errores de carga de rutas tienen una página `+error.svelte` accesible y no exponen detalles internos.

## 2. Diagnóstico previo

En el HEAD base `ddcbff1ade55077e26cfab1` (antes de la implementación F1.1):

- `src/routes/+layout.svelte` inicializaba tema e i18n en `onMount`, pero ante una excepción marcaba `data-app-state="error"` y relanzaba el error. No ofrecía recuperación en ese nivel.
- El layout raíz renderizaba inmediatamente los hijos mientras los inicializadores de cliente todavía no habían terminado.
- `src/routes/(app)/+layout.svelte` ejecuta el bootstrap de sesión de forma independiente en su propio `onMount`; esa responsabilidad se mantiene separada y no se declara terminada por F1.1.
- `SessionBootView` cubría la validación de sesión, no los fallos de inicialización general ni errores de renderizado de rutas.
- `src/app.html` no declaraba explícitamente el estado inicial de readiness.

## 3. Cambios implementados

| Archivo | Cambio | Ownership |
|---|---|---|
| `src/lib/platform/appBootstrap.ts` | Secuencia única y determinista: tema y después i18n. Propaga errores al coordinador raíz para que gestione estado/reintento. | Plataforma / bootstrap |
| `src/lib/components/AppStartupView.svelte` | Vista de carga inicial y fallo de bootstrap con acción de reintento; respeta movimiento reducido. | UI compartida |
| `src/routes/+layout.svelte` | Controla `initializing/ready/error`; no renderiza rutas hasta completar bootstrap; captura error de init; reintento; boundary para fallos de render y recuperación de vista/recarga. | PLAT-BOOT-001 |
| `src/app.html` | SSR emite `data-app-state="initializing"` y `data-app-ready="false"`, evitando que smoke/E2E observen ready antes de hydration/bootstrap. | PLAT-BOOT-001 |
| `src/routes/+error.svelte` | Fallback de errores de carga/ruta con estado HTTP, reintento y regreso al inicio; no muestra stack ni mensaje interno. | ROUTING-001 / PLAT-BOOT-001 |
| `src/test/unitTest/platform/appBootstrap.test.ts` | Verifica orden de inicialización, propagación de fallo y posibilidad de reintento. | Plataforma / pruebas |

## 4. Comportamiento y límites

- `data-app-state` admite `initializing`, `ready` y `error`; `data-app-ready` es `true` solo en `ready`.
- El atributo es una señal de observabilidad/smoke, no un control de autorización.
- La inicialización de tema/i18n es browser-only porque se ejecuta desde `onMount`; el SSR conserva una salida determinista de carga para evitar discrepancias de hydration.
- Si falla un inicializador, el siguiente no se ejecuta; el error se presenta como estado recuperable, no se relanza desde el callback de bootstrap.
- Los errores descendientes capturados por `svelte:boundary` presentan fallback con reintento local o recarga completa.
- La página `+error.svelte` cubre errores de carga/navegación gestionados por SvelteKit. No reemplaza el boundary de render ni la recuperación de bootstrap.
- La validación de sesión, permisos y almacén sigue perteneciendo a sus owners Auth/Warehouses y a F1.3–F1.5. La señal raíz `ready` no significa que la sesión esté autenticada ni que una ruta esté autorizada.
