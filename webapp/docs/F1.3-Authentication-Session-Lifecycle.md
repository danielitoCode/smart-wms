# F1.3 — Login, logout, restauración de sesión, expiración y errores de autenticación

- **Estado:** IN_PROGRESS — auditoría inicial completada; implementación y validación pendientes.
- **Rama:** `svelte-webapp`
- **Fecha de auditoría:** 27-11-2026
- **Snapshot inspeccionado:** `2d3e8a50361e8caa886fc0c2d874dbef5e4cce0f`
- **Ámbito:** exclusivamente `webapp/`; Flask es contrato de referencia y no se modifica.
- **Peso:** 1,5%; todavía no acreditado.

## 1. Objetivo

Completar y verificar el ciclo de vida de autenticación en SvelteKit: login, restauración tras recarga, logout, expiración, errores de sesión y consistencia entre pestañas. La cookie HttpOnly y las decisiones de autenticación del backend siguen siendo la autoridad. El frontend solo conserva una proyección temporal de identidad y permisos.

F1.3 no debe duplicar F1.6: la normalización HTTP y la política común de 401/403 pertenecen al cliente HTTP. F1.3 define el comportamiento de sesión y su integración con el cliente; los cambios transversales en ApiClient deben coordinarse con F1.6 y no crear un segundo mecanismo de errores.

## 2. Contrato backend documentado (sin cambios)

Según `R0-Platform-Contracts.md` y `R0-Session-Grants-Integration.md`:

| Operación | Contrato conocido | Implicación frontend |
|---|---|---|
| `POST /api/auth/login` | Valida credenciales, aplica rate limit y emite cookie de sesión y CSRF. | No guardar el token devuelto en localStorage/sessionStorage. |
| `GET /api/auth/me` | Requiere sesión y devuelve identidad/grants actuales. | Fuente para restauración y snapshot de permisos. |
| `POST /api/auth/refresh` | También requiere sesión válida; no recupera una cookie ya expirada. | No intentar refresh después de 401 de `/me`; solo usarlo si existe un flujo explícito de renovación de sesión todavía válida. |
| `POST /api/auth/logout` | Revoca/limpia cookies; con cookie válida requiere doble-submit CSRF. | El estado local debe limpiarse inmediatamente, pero la UI debe distinguir fallo de confirmación remota. |
| `POST /api/auth/change-password` | Requiere sesión y CSRF; cambia contraseña. | Mantener el comportamiento actual y la prioridad de `must_change_password`. |

No se cambia el backend ni se asume que un refresh pueda renovar una sesión expirada.

## 3. Estado actual inspeccionado

### 3.1 Login

- `AuthRemoteDataSource` usa `POST /api/auth/login` y después `GET /api/auth/me`.
- `AuthRepositoryImpl.login` ignora deliberadamente el token de cuerpo como credencial cliente; obtiene los grants completos de `/me` y escribe `AuthSession` solo si no cambió la generación de sesión.
- `LoginUseCase` valida usuario/contraseña no vacíos y rechaza usuario inactivo.
- `loginState` controla loading, evita doble submit, limpia password después del intento y traduce 401/429/red a mensajes.
- `LoginScreen` conserva redirects internos seguros de F1.2 y prioriza `/change-password`.

### 3.2 Restauración

- `AuthSession` es exclusivamente memoria; no persiste credenciales ni identidad.
- `AuthBootHint` guarda solo `smartwms.authBoot=1` en localStorage para distinguir una primera visita anónima de una sesión previa expirada. No es prueba de autenticación.
- `SplashScreen` llama `/me` al entrar en `/`; si la cookie es válida, calcula home con los grants; si es inválida y existe hint, dirige al login; una visita anónima sin hint va a landing.
- El layout protegido verifica `/me` al montar y vuelve a validar grants en navegación interna.
- `AuthRepositoryImpl.sessionEpoch` evita que un login o `/me` tardío vuelva a establecer identidad después de logout.

### 3.3 Logout

- `AuthRepositoryImpl.logout` incrementa `sessionEpoch`, limpia `AuthSession` antes de llamar al endpoint y vuelve a limpiarlo en `finally`.
- `authGuardState.logout` limpia usuario/estado y elimina el hint de bootstrap.
- El shell sincroniza el contexto de almacén a null y navega a `/login`.
- `ApiClient` ya incluye `credentials: 'include'` y cabecera CSRF en métodos mutables.

### 3.4 Expiración y errores

- `EnsureAuthenticatedUseCase` consulta `/me`; un error clasificado como auth limpia el snapshot. Errores de red/5xx no borran una identidad previamente validada.
- La prueba existente confirma que un 401 no dispara refresh, coherente con el contrato Flask.
- El layout revalida al cambiar de ruta, pero no se observa una notificación global desde respuestas 401 de cualquier feature ni sincronización explícita de cierre de sesión entre pestañas.
- `ApiError.isAuth` agrupa 401 y 403; `EnsureAuthenticatedUseCase` los trata ambos como sesión no autorizada. El contrato general distingue 401 (sesión) de 403 (permiso/scope). Antes de cambiar el comportamiento, verificar el status real que devuelve específicamente `/api/auth/me` para cada condición; no convertir un 403 de un endpoint de negocio en logout global.
- En `SplashScreen.navigateFromOutcome()`, el resultado `kind: 'login'` navega a `/login` sin transferir `result.message`; se pierde el mensaje de sesión expirada o servidor no disponible.
- `authGuardState.logout` absorbe el fallo remoto sin exponer un resultado al shell; la navegación a login ocurre aunque Flask no haya confirmado la eliminación de cookie.

## 4. Gaps confirmados y prioridades

| ID | Hallazgo | Prioridad | Trabajo propuesto |
|---|---|---:|---|
| F13-01 | El fallo remoto de logout se silencia; la UI no puede informar que el servidor no confirmó el cierre. | Alta | Mantener limpieza local inmediata, propagar/representar el resultado remoto y mostrar estado inequívoco sin restaurar la identidad local. |
| F13-02 | Splash pierde el mensaje de expiración/indisponibilidad al navegar a login. | Alta | Transportar un motivo seguro/no sensible a LoginScreen y mostrarlo una sola vez. |

| F13-04 | Las respuestas 401 de features no invalidan globalmente la sesión de inmediato. | Alta, coordinada con F1.6 | Definir un evento central de sesión expirada en ApiClient y consumidor único en shell; excluir login/logout/me para evitar bucles y duplicación. |

## 5. Plan de implementación incremental

1. **F1.3-A — Contrato de estados y mensajes:** definir estados de sesión (`checking`, `authenticated`, `anonymous`, `unavailable`, `logout-unconfirmed`) y cómo se muestran los mensajes de expiración/indisponibilidad. No filtrar detalles del backend.
2. **F1.3-B — Logout observable y resistente a fallos:** limpiar estado local/warehouse inmediatamente, invalidar respuestas pendientes y exponer si Flask confirmó el logout. No afirmar que la cookie fue revocada si la llamada falló.
3. **F1.3-C — Coordinación entre pestañas:** publicar/escuchar solo eventos de invalidación; al recibirlos, limpiar memoria y contexto warehouse y navegar a login con retorno seguro. El servidor sigue siendo autoridad.
4. **F1.3-D — Expiración por 401:** acordar interfaz con F1.6 para emitir un único evento global en 401 de endpoints protegidos; no hacer logout por 403 de negocio. Evitar interceptar login fallido como sesión expirada.
5. **F1.3-E — Restauración y feedback:** conservar mensajes de sesión expirada/servidor no disponible al llegar a LoginScreen; verificar recarga y deep link usando F1.2.
6. **F1.3-F — Pruebas:** unitarias de estado, carreras y sincronización; integración HTTP de cookie/CSRF/logout; E2E de login/logout/restauración/expiración y navegación protegida.

Cada bloque debe tener pruebas antes de avanzar al siguiente. No se cambia Flask.

## 7. Límites y reglas anti-regresión

- No persistir token, cookie, contraseña, grants ni perfil en almacenamiento web.
- No introducir refresh automático tras 401: el endpoint Flask exige sesión válida.
- No confundir 403 de permiso/scope con expiración sin verificar el endpoint y contexto.
- No permitir que fallos de red borren silenciosamente una sesión válida en memoria.
- No permitir que respuestas asíncronas anteriores a logout repueblen `AuthSession`.
- Mantener F1.1 bootstrap/readiness y F1.2 redirects/aliases sin regresiones.
- Coordinar la invalidación global por 401 con F1.6; evitar dos interceptores o estados de sesión paralelos.
- No atribuir a F1.3 componentes visuales independientes ni cambios Flask.

## 9. Implementación incremental — F1.3-A y F1.3-B

**Estado de bloques:** F1.3-A implementado; F1.3-B implementado. Validación CI/local pendiente sobre el HEAD que contiene estos cambios. No se acredita todavía el 1,5% de F1.3.

### 9.1 F1.3-A — Contrato de estados y mensajes

- `AuthGuardStatus` ahora distingue `checking`, `authenticated`, `anonymous`, `unavailable` y `logout-unconfirmed`. La indisponibilidad de backend/red deja de modelarse como un estado genérico `error`.
- `SplashOutcome` transporta códigos de aviso seguros (`session-expired`, `account-inactive`, `service-unavailable`) en vez de perder el motivo al navegar a `/login` o copiar texto arbitrario del servidor a la URL.
- `SplashScreen` pasa el código de aviso a login y `LoginScreen` presenta mensajes localizados. Los mensajes no contienen tokens, cookies ni detalles internos de Flask.
- `notice=logout-unconfirmed` evita que LoginScreen redirija automáticamente al área autenticada si el servidor no confirmó el logout. Así no se oculta el aviso mientras la cookie HttpOnly podría seguir siendo válida.

### 9.2 F1.3-B — Logout observable y resistente a fallos

- `AuthRepository.logout()` devuelve un resultado discriminado: `{ confirmed: true }` o `{ confirmed: false, reason: 'remote-unavailable' }`.
- El repositorio incrementa `sessionEpoch` e invalida `AuthSession` antes de llamar a Flask; vuelve a limpiar el snapshot en `finally`.
- Un fallo de red/servidor ya no se silencia ni se propaga como una excepción de flujo no controlada: se comunica como logout no confirmado. El frontend no afirma que Flask haya revocado la cookie.
- `authGuardState.logout()` elimina usuario y `AuthBootHint` en ambos resultados, y expone el estado `logout-unconfirmed` cuando no hay confirmación remota.
- El shell limpia el contexto de almacén y navega a `/login?notice=logout-unconfirmed`; la pantalla muestra una advertencia explícita y no auto-redirige de vuelta al área protegida.

### 9.3 Pruebas añadidas/ajustadas

`AuthHttpIntegration.test.ts` ahora verifica tanto el logout confirmado como el no confirmado: método POST, `credentials: include`, resultado observable y limpieza de `AuthSession` aun cuando Flask responde 500.

La cobertura sigue siendo HTTP simulado: no demuestra todavía el borrado real de cookie en navegador ni el comportamiento multi-tab. Eso corresponde a F1.3-C/F1.3-F.
