# F3.8 — Transfer Orders: cierre y bloqueos pendientes

Rama: `svelte-webapp`  
Alcance de migración: únicamente `webapp/`. El backend Flask/Python se consulta como contrato y no se modifica en esta fase.

## Cambios aplicados en webapp

- El modelo de aprobación admite `lines_snapshot` como dato opcional y tipado. El mapper conserva las líneas históricas con `to_line_id`, `item_id` y `picked_in_snapshot`.
- El detalle de cada aprobación muestra las cantidades capturadas en el snapshot. Si el servidor omite el campo, la UI lo indica expresamente; no reconstruye un histórico a partir de las cantidades actuales.
- La validación del formulario de importación queda alineada con el límite del contrato de Transfer Orders: `quantity <= 1,000,000`.
- Se amplían las pruebas del mapper para el snapshot y del caso de uso para el límite superior.

## Avance de F3.8-A y F3.8-B (frontend)

### F3.8-A — estado y presentación

- La pantalla separa ahora el faltante inicial (`requested - committed`), la reserva pendiente (`committed - approved`) y lo recogido que aún espera aprobación (`picked - approved`). Los valores derivados se limitan a cero para evitar mostrar cantidades negativas ante datos inconsistentes.
- Se muestra un resumen agregado por transferencia además del detalle por línea.
- El historial muestra también la fecha de rechazo cuando el contrato la devuelve.
- Se conserva la distinción entre snapshot vacío (`lines_snapshot.lines = []`) y snapshot no disponible (`lines_snapshot` ausente/null). No se reconstruye información histórica desde las cantidades actuales.
- Las asignaciones concretas por bin/lote siguen sin poder mostrarse: el DTO de detalle no contiene una relación de reservas por línea e inventario/bin.

### F3.8-B — operaciones desde UI

- Se alinearon las condiciones de inicio de picking, envío y short-close con los estados de línea conocidos por la máquina de estados backend (`PENDING`, `PARTIALLY_PICKED`, `PICKED`), evitando ofrecer acciones sobre líneas terminales/desconocidas.
- Las operaciones existentes siguen usando rutas específicas: start-picking, submit picker result, approve, reject, cancel y short-close. La pantalla bloquea acciones concurrentes mientras `saving` está activo y exige confirmación para mover inventario, cancelar y cerrar faltantes.
- La eliminación ya no borra el detalle seleccionado antes de recibir éxito del servidor. Ante un conflicto/error conserva el contexto para que el usuario pueda corregir o reintentar.
- Se añadieron pruebas de estado para eliminación exitosa/fallida y pruebas UI para cantidades e historial de aprobación.

### Verificación pendiente de esta iteración

Los cambios se han escrito en la rama mediante GitHub; esta sesión no dispone de un runner local para ejecutar Vitest, `svelte-check` o build. Por tanto, las pruebas añadidas no se declaran aprobadas hasta que CI las ejecute. El contrato backend continúa omitiendo `lines_snapshot` del detalle y no expone reservas persistentes por bin/lote; esas dos limitaciones no pueden resolverse exclusivamente en `webapp/`.

## Bloqueos que impiden cerrar F3.8

### 1. Reserva persistente por línea y bin — BLOQUEANTE

El importador backend reserva mediante `inventory.quantity_allocated` y recorre las filas de inventario del artículo/almacén. Sin embargo, el contrato de lectura de Transfer Orders devuelve líneas con cantidades agregadas y no devuelve una asignación persistida `to_line_id -> inventory_id/bin_id/lot_number/quantity`.

Los helpers de liberación/cancelación y short-close vuelven a recorrer las filas con asignación positiva en orden de `inventory_id`; no identifican qué fracción pertenece a cada línea/orden. Con órdenes simultáneas del mismo SKU, ese algoritmo no demuestra que se libere la reserva propietaria correcta. La UI no puede corregirlo ni inventar una asignación de bins.

**Requisito de backend para cerrar:** persistir una tabla/relación de reservas por orden, línea, fila de inventario/bin, lote y cantidad; crearla dentro de la transacción de importación; consumirla por picking/aprobación; liberar exactamente sus remanentes en rechazo/cancelación/short-close; bloquear y validar las filas en orden determinista. Exponer la asignación en DTO si el usuario debe auditarla.

### 2. Alinear picking, aprobación, cancelación y short-close — BLOQUEANTE

La UI bloquea el envío de un nuevo resultado mientras existe una aprobación pendiente y bloquea cancelación cuando hay aprobaciones. No obstante, la corrección integral depende de la reserva por línea/bin anterior.

La revisión del backend también revela una regla que debe validarse/corregirse allí: al rechazar un snapshot, la restauración de estado de línea puede asignar `APPROVED` cuando `restored_picked == committed_qty`, aunque la cantidad restaurada no necesariamente sea igual a `approved_qty`. La migración frontend no debe emular ni ocultar esa transición.

**Requisito de cierre:** pruebas de flujo con dos o más envíos secuenciales, aprobación parcial, rechazo, re-picking, short-close y cancelación; comprobar cantidades asignadas, disponibles, recogidas, aprobadas y liberadas en cada paso.

### 3. Exponer `lines_snapshot` por aprobación — ALTA

El backend sí consulta y utiliza `transfer_order_approvals.lines_snapshot` para aprobar/rechazar, pero `_serialise_to_approval` no lo incluye en la respuesta de detalle. Por tanto, la nueva UI solo podrá mostrarlo cuando el contrato backend lo exponga.

**Requisito de backend:** incluir el objeto `lines_snapshot` sin transformaciones destructivas en cada aprobación del endpoint de detalle. Añadir prueba de contrato que compare el snapshot persistido con el devuelto.

### 4. Pruebas de almacenes, concurrencia y reservas simultáneas — ALTA

Las pruebas actuales de F3.8 cubren validaciones de casos de uso, mapeo básico, rutas y repositorio. No prueban concurrencia real, aislamiento entre dos órdenes que reservan el mismo artículo, reservas por bin/lote, permisos cruzados entre almacenes ni integridad tras rollback.

**Requisito de cierre:** pruebas de integración backend contra PostgreSQL con dos transacciones concurrentes; pruebas multi-almacén (acceso a ambos almacenes y denegación si falta uno); asserts de no sobreasignación y liberación exacta. Desde webapp, añadir pruebas de estado/UI para errores 409, recarga tras acciones y doble interacción.

### 5. Límite de cantidades y pruebas UI/estado — MEDIA

La pantalla tenía un límite de 100.000 mientras que `TransferOrderImportRow` acepta hasta 1.000.000. La validación visible ya se alineó a 1.000.000 y se añadió una prueba del límite del caso de uso. Aún falta prueba de pantalla/estado para 1.000.000, 1.000.001, errores 422 por fila, 409 por concurrencia y estados de carga/doble envío.

## Verificación

No se ejecutó `npm run check`, `npm test` ni `npm run build` desde este cambio: las escrituras se hicieron mediante GitHub y no hay un runner local conectado a esta sesión. El commit más reciente no tiene checks de CI reportados al consultarlo.

## Decisión de cierre

**F3.8 permanece ABIERTO.** Los puntos 1 y 2 requieren corrección del backend y pruebas transaccionales. Los puntos 3 y parte de 4 también necesitan cambios/contratos backend. Los cambios frontend realizados son compatibles y visibles, pero no sustituyen esas garantías.
