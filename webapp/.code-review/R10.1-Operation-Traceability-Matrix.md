## 1. Regla de lectura

Esta matriz desglosa las rutas en grupos de operaciones de negocio. No certifica equivalencia solo por compartir una pantalla, DTO o endpoint. Los estados significan:

- `PARTIAL_TRACEABILITY`: correspondencia inicial localizada; falta cotejo de handlers React, casos de uso, pruebas y evidencia de comportamiento.
- `CONTRACT_DOCUMENTED`: endpoint, permiso y semántica descritos en el contrato Flask; no implica E2E.
- `BACKEND_LIMITATION`: la capacidad o garantía no existe en el contrato Flask inspeccionado.
- `PENDING_EVIDENCE`: falta evidencia de ejecución comparativa.
- `VERIFIED_PARITY`: reservado para R10.3/R10.4 con recorrido repetible, misma precondición y mismo resultado persistido.

Los nombres de DTO se consignan cuando están identificados en el contrato. Cuando la respuesta es route-defined, no se inventa un DTO nominal.

## 3. Reglas transversales obligatorias

1. **React source:** completar cada fila con archivo, handler/evento, validación, mutación y estado siguiente. Las rutas de `App.jsx` solo son el punto de entrada.
2. **Use cases:** registrar el nombre exacto de cada UseCase/UseCases y la policy Domain llamada; no basta la carpeta de feature. La columna actual es una primera localización.
3. **DTO:** contrastar request Pydantic y response JSON real (envelope, nullability, paginación, errores) con DTO/mapper Svelte. Un DTO de request no define automáticamente el DTO de response.
4. **Permisos:** registrar el page/function grant que usa el frontend y el decorador exacto Flask. El route guard Svelte es UX, no seguridad de API.
5. **Warehouse scope:** clasificar cada endpoint como `SERVER_ENFORCED`, `FRONTEND_GUARD_ONLY`, `GLOBAL` o `NOT_APPLICABLE`. Un query param `warehouse_id` no demuestra autorización.
6. **Pruebas:** enlazar test exacto por operación (Domain, Application, Data/DTO, UI/State, Integration) y anotar qué demuestra. Test con mock no demuestra persistencia Flask.
7. **Resultado:** solo `VERIFIED_PARITY` después de R10.3/R10.4 con snapshot inicial, requests/responses y estado final comparado.

## 4. Limitaciones ya conocidas que deben permanecer visibles

- R1: endpoints administrativos Zones/Bins no demuestran warehouse scope consistente; Items es catálogo global. UOM y capacidades físicas de bins no están en el contrato inspeccionado.
- R3: listado de inventario no tiene enforcement server-side explícito de warehouse scope; no hay preview server-side para ajuste directo ni ledger completo de movimientos; audit-log global no sustituye ledger.
- R6: el flujo picking/packing/shipping vive en pantallas operativas Svelte y no en mirrors React; se valida contra el contrato operativo Flask y las reglas documentadas, no contra una pantalla React inexistente.
- R8: Audit Log y CRUD administrativo de warehouses son globales/no scoped; imports no valida cada warehouse/bin anidado por fila; settings son globales.
- R9: Webhooks/Audit Log globales; Fraud sin score/recommendation; Customers es proyección read-only sin identidad canónica.
- Ninguna de estas limitaciones se corrige inventando datos ni alterando Flask dentro de esta fase.

### 8.4.3 Contratos Flask confirmados

**A. Lookup y recepción operativa**
- `GET /api/receiving/po/<barcode>`: requiere auth; aplica `warehouse_scope_clause("warehouse_id")` al SELECT de PO. PO fuera del scope y PO inexistente producen 404; PO CLOSED produce 400. Respuesta incluye PO y líneas con sku, item_name, upc, mpn, ordered, received, remaining y status.
- `POST /api/receiving/receive`: requiere auth + `ReceiveItemsRequest`; `po_id > 0`, lista no vacía, item/bin > 0, quantity 1..100000, lot/serial <=100, notes <=1000. La PO se selecciona con warehouse scope y `FOR UPDATE`; cada línea se valida contra la PO y el over-receipt está bloqueado por defecto. La operación registra item_receipts, actualiza inventory y PO line, audit y `receipt.completed/1`; batch rechazado no debe dejar cambios parciales.
- Svelte datasource `ReceivingRemoteDataSource` corresponde con estos contratos para lookup y receive. Envía `po_id`, items `item_id/quantity/bin_id` y opcional `lot_number`; no transmite serial_number ni notes, aunque el schema Flask los admite.

**B. Cancelación de sesión — no confundir con unreceive**
- `POST /api/receiving/cancel`: auth + `CancelReceivingRequest`; exige `po_id > 0`; `receipt_ids` puede estar vacío y `warehouse_id` es opcional. El empty list responde 200 "Nothing to cancel".
- El endpoint usa warehouse scope al localizar receipts, rechaza receipt IDs visibles de otra PO (400) y omite silenciosamente receipts fuera del scope/no encontrados. Revierte inventory en el bin original con floor 0, quantity_received y estado de línea; borra item_receipts; recalcula estado de PO; escribe audit por warehouse.
- El Svelte datasource envía exactamente `{po_id, receipt_ids}`, por lo que sí está alineado con el contrato de cancelación batch. No envía warehouse_id (correcto: el backend debe derivar scope del usuario).
- Esta ruta no acepta `reason`, no devuelve el detalle de cada receipt y no sustituye el endpoint administrativo de unreceive.

**C. Historial y unreceive administrativo**
- `GET /api/admin/purchase-orders/{po_id}/receipts`: auth + permiso de página `receiving`; devuelve receipt_id, PO line, item/SKU, quantity, bin, warehouse, receiver, timestamp, lot/serial/notes/external_id.
- `POST /api/admin/receipts/{receipt_id}/unreceive`: auth + permiso `receiving`; body opcional `{reason}`; reason debe ser string y máximo 500 chars. Errores: 404 not_found; 409 insufficient_available; 422 not_a_po_receipt/validación. Éxito devuelve receipt_id, po_id, po_status, quantity_reversed y bin_decrements.

**D. Lifecycle PO**

### Corrección backend de warehouse scope

- `list_purchase_orders`: filtra SQL por `warehouse_scope_clause("warehouse_id")`, además de filtros del cliente.
- `get_purchase_order`, `update_purchase_order`, operaciones de líneas, `close_purchase_order` y `reopen_purchase_order`: primero seleccionan el PO dentro del scope; un PO fuera de scope se presenta como 404.
- `list_po_receipts`: valida el PO bajo scope y filtra las filas de receipts por `r.warehouse_id`.
- `unreceive_receipt`: realiza preflight de receipt ID dentro del scope antes de invocar `record_unreceive`.
- `cancel_receiving`: valida que el PO target pertenezca al scope antes de programar el recálculo del estado. Se elimina el riesgo de recalcular un PO arbitrario a partir del body con IDs vacíos/invisibles/stale.
- `create_purchase_order` ya recibe `warehouse_id` en el body y el middleware de auth aplica la allow-list a ese campo; se añadió test de rechazo de creación en warehouse no asignado.
- Las rutas mantienen sus grants originales: `purchase-orders` para administración PO; `receiving` para historial/unreceive; `require_auth` y scope de warehouse para las rutas operativas.
