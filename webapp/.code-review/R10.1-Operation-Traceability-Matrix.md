## 1. Regla de lectura

Esta matriz desglosa las rutas en grupos de operaciones de negocio. No certifica equivalencia solo por compartir una pantalla, DTO o endpoint. Los estados significan:

- `PARTIAL_TRACEABILITY`: correspondencia inicial localizada; falta cotejo de handlers React, casos de uso, pruebas y evidencia de comportamiento.
- `CONTRACT_DOCUMENTED`: endpoint, permiso y semántica descritos en el contrato Flask; no implica E2E.
- `BACKEND_LIMITATION`: la capacidad o garantía no existe en el contrato Flask inspeccionado.
- `PENDING_EVIDENCE`: falta evidencia de ejecución comparativa.
- `VERIFIED_PARITY`: reservado para R10.3/R10.4 con recorrido repetible, misma precondición y mismo resultado persistido.

Los nombres de DTO se consignan cuando están identificados en el contrato. Cuando la respuesta es route-defined, no se inventa un DTO nominal.

## 3. Reglas transversales obligatorias

1. **React source:** completar cada fila con archivo, handler/evento, validación, mutación y estado siguiente. Las rutas de `App.jsx` solo son el punto de entrada.
2. **Use cases:** registrar el nombre exacto de cada UseCase/UseCases y la policy Domain llamada; no basta la carpeta de feature. La columna actual es una primera localización.
3. **DTO:** contrastar request Pydantic y response JSON real (envelope, nullability, paginación, errores) con DTO/mapper Svelte. Un DTO de request no define automáticamente el DTO de response.
4. **Permisos:** registrar el page/function grant que usa el frontend y el decorador exacto Flask. El route guard Svelte es UX, no seguridad de API.
5. **Warehouse scope:** clasificar cada endpoint como `SERVER_ENFORCED`, `FRONTEND_GUARD_ONLY`, `GLOBAL` o `NOT_APPLICABLE`. Un query param `warehouse_id` no demuestra autorización.
6. **Pruebas:** enlazar test exacto por operación (Domain, Application, Data/DTO, UI/State, Integration) y anotar qué demuestra. Test con mock no demuestra persistencia Flask.
7. **Resultado:** solo `VERIFIED_PARITY` después de R10.3/R10.4 con snapshot inicial, requests/responses y estado final comparado.

## 4. Limitaciones ya conocidas que deben permanecer visibles

- R1: endpoints administrativos Zones/Bins no demuestran warehouse scope consistente; Items es catálogo global. UOM y capacidades físicas de bins no están en el contrato inspeccionado.
- R3: listado de inventario no tiene enforcement server-side explícito de warehouse scope; no hay preview server-side para ajuste directo ni ledger completo de movimientos; audit-log global no sustituye ledger.
- R6: el flujo picking/packing/shipping vive en pantallas operativas Svelte y no en mirrors React; se valida contra el contrato operativo Flask y las reglas documentadas, no contra una pantalla React inexistente.
- R8: Audit Log y CRUD administrativo de warehouses son globales/no scoped; imports no valida cada warehouse/bin anidado por fila; settings son globales.
- R9: Webhooks/Audit Log globales; Fraud sin score/recommendation; Customers es proyección read-only sin identidad canónica.
- Ninguna de estas limitaciones se corrige inventando datos ni alterando Flask dentro de esta fase.
